# Steppy

Python CLI tool that generates Playwright pytest files from Markdown scenario files.
Code generator, not a runtime engine — generated tests are standalone.

## Commands

- `python -m pip install -e .` — required before running tests (hatchling build)
- Releasing: bump every version (`tests/test_versions_aligned.py`), then push a `vX.Y.Z` tag. `release.yml` builds and checks the wheel and sdist, creates the GitHub Release, publishes `steppy-dev` to PyPI through Trusted Publishing once the `PYPI_PUBLISH` repository variable is `true`, and publishes the npm packages once an `NPM_TOKEN` secret exists. One-time setup: `CONTRIBUTING.md`, "Releasing".
- `python -m pytest tests/ --ignore=tests/e2e -q` — run all unit tests (e2e is generated, skip it)
- `ruff check . && ruff format --check .` — lint + format gate; config is `[tool.ruff] line-length = 120` in `pyproject.toml`, lint selection is the defaults + `TD` (TODO-tag discipline; `seed/**` exempt). Note: `_totp_now` in `src/steppy/totp.py` is byte-mirrored in `templates/conftest.py.j2` (guard: `tests/test_totp.py`) — apply any formatter change to both. Developers may invoke Ruff through their preferred environment manager, such as `uv run ruff`.
- `steppy generate` — regenerate test files from scenarios (with `tours.enabled`: also the in-app tour files, and a `test_<slug>__tour` replay appended to each tour's scenario test)
- `steppy tours` — compile in-app tours only: `<output.tours_dir>/<build-id>/` plus a flat copy into each `app-assets` target; tests untouched. `--check` (CI freshness gate, writes nothing: compares only the committed `app-assets` copies, by content, for the build id each copy records — the canonical tree is gitignored and a `git-sha` copy always lags HEAD, so a differing id is a note, never a failure), `--dry-run`, `--build-id ID` (this command only), `--explain`, `-d`. See `docs/tours.md`.
- `steppy validate` — check scenario files for errors
- `steppy record [URL] --role <role> --slug <name>` — record a browser session via `playwright codegen` and post-process it into a **draft** `scenarios/<name>.md` (`record_cli.py`, a leaf module). Collapses a login sequence to `- action: login`, placeholderizes detected secret fields to `${VAR}` refs (resolved at run time by the `_interp_val` conftest helper), prints a paste-ready `screenshot.mask`, runs the selector lint. Loads `.auth/<role>.json` for an authenticated session unless `--no-auth`. V1/CLI-plumbing — a draft for review, not a finished scenario.
- `steppy guide --tag user-guide-<role>` — render HTML/Markdown guides from captured screenshots
- `steppy run --guide` — run only scenarios with `guide.enabled: true` (auto-enables screenshots **and `--no-asserts`**, sets `STEPPY_GUIDE_MODE=1`; auto-parametrizes over every locale in `config.yaml` and every layout in `screenshot.layouts`)
- `steppy run --locales fr,nl` — explicitly parametrize a run over locales (overrides the `--guide` default; use to capture a subset)
- `steppy run --layouts desktop,mobile` — parametrize a run over layouts at the configured viewports. Works in both test mode (verify scenarios across device sizes) and guide mode (overrides the auto-derived layouts)
- `steppy run --no-asserts` — set `STEPPY_NO_ASSERTS=1` so generated tests skip every `expect()` (auto-enabled by `--guide`; for explicit multi-locale capture without `--guide`)
- `steppy guide --guide` — assemble guides for every `guide.enabled` scenario across all its `user-guide-*` tags
- `steppy build` — generate guide artifacts from a TS config; target chosen by the config's `target` field (`static` default for a framework-agnostic self-contained site, or `angular` for standalone Angular components)
- `steppy build --config path/to/config.ts` — use a custom config path (default: `steppy.guide.config.ts`)
- `steppy build --dry-run` — preview what files would be generated without writing
- `steppy guide --pdf` / `--handbook`, `steppy build --pdf` / `--handbook` — print the generated guide pages to PDF via headless Chromium, and/or assemble every guide into one handbook document (HTML + PDF). Paper settings come from the `pdf:` block in `config.yaml`; `build` is static-target only
- `steppy guide --video` / `steppy build --video` — render a narrated MP4 (+ WebVTT + poster) per (guide × locale × layout) for guides declaring `modes: ['video']`. **Two gates**: the mode is the content decision, the flag the cost one. Both build targets. Requires ffmpeg. Settings live in the `video:` block; narration provider in `video.tts`. **Unrelated to `steppy run --video`**, which records Playwright debugging footage of failed tests
- `steppy video check` — verify ffmpeg / ffprobe / Chromium / the TTS provider / the API key before a long render finds out one at a time
- `steppy video cache` — report both render caches; `--prune-older-than N` (days) / `--max-size N` (MB) reclaim least-recently-**used** entries first, `--clear` empties, `--tts`/`--video` scope to one. Both caches are content-addressed and so grow monotonically; nothing else ever collects them
- `steppy run --workers N` — opt-in parallel execution: spin up N Docker Compose stacks with one steppy-worker container each, pulling scenarios from a shared queue. N=1 (or unset) = unchanged single-process path with no Docker. Requires `parallel:` block + per-app `internal_url` in `config.yaml` and Docker Compose 2.20+. For `mode: storage-state` auth, add a `parallel.pre_auth` command to capture the in-network origin before dispatch (storage state is origin-bound; see the pre_auth pattern below), or `parallel.isolate_auth: true` to give each worker a private `.auth` dir instead. `--trace`/`--video`/`--retries`/`-- <pytest args>` all reach the workers.
- `steppy run --retry-pass N` / `--strict-flaky` / `--no-fail-fast` — parallel-only run modifiers. `--retry-pass` overrides `parallel.retry.passes` (default 1; `0` disables) — after the queue drains, failed scenarios re-run at reduced concurrency and a pass-on-retry is reported as **FLAKY** without failing the build. `--strict-flaky` makes flakes fail the build; `--no-fail-fast` disables the circuit breaker for one run.
- `steppy stacks cleanup` — rescue command: tears down orphaned `steppy-run-*` Compose projects left by a force-killed parallel run.
- `steppy migrate custom` — rewrite mechanical `action: custom` blocks as declarative steps. `--dry-run` (default) previews, `--write` applies, `--diff` shows each rewrite, `--skipped` lists what was left alone and why, `--report FILE` dumps JSON. A block converts only when **every** statement matches a rule AND the rewrite verifies (generated code parses, no selector lost, operations conserved up to `verify.SUBSTITUTIONS`); anything else is reported, never touched. Measured on the live corpora: 2 455 of 5 032 blocks (49%) in one project, 5 of 251 in the other — the low number is the honest one, that project's residue is genuinely imperative.
- `steppy flaky` — rank scenarios by flake rate across recent runs, from the history parallel runs append to `.steppy/history.jsonl`. `--last N` (window, default 20), `--min-rate`, `--limit`, `--json`, `--prune N`. Parallel runs only (the single-worker path produces no per-scenario records).
- `steppy run --coverage` — record per-scenario coverage signals (route trail, API requests, V8 JS coverage via CDP) into `output/coverage/raw/<run_id>/` and auto-merge them into the map store post-run. Composes with `--scenario`/`--tag`/`--guide`/`--workers` like the other mode flags.
- `steppy run --bundle` — capture the extra artifacts a results bundle needs: per-test **and per-step** event records under `output/events/<run-id>/`, JUnit XML under `output/junit/<run-id>/`, and an `output/.steppy-run.json` recording the run spec. Off by default because it changes the pytest invocation. Composes with every other run flag, single-worker and `--workers N` alike. Step records are what give `manifest.tests[].failed_step` its value; export `STEPPY_STEP_EVENTS=0` to keep the rest and drop those.
- `steppy bundle create|inspect|verify` — package one run's `output/` tree into a portable `.tar.zst` (`.tar.gz` without the `steppy-dev[bundle]` extra). The archive holds `output/` **exactly as steppy wrote it** — no path rewriting — so unpacking it yields a tree `steppy guide` / `steppy build` consume unchanged, plus a generated `manifest.json`, a merged `junit.xml`, and `events/*.jsonl`. `inspect` prints the manifest without extracting; `verify` re-hashes every member against it. Useful with no control plane at all: a self-describing run archive to attach to a CI job.
- `steppy bundle upload [BUNDLE]` — push one run's results to a Steppy control plane. Content-addressed: the manifest is offered, the server returns presigned PUT URLs **only for digests it does not already hold**, and finalize verifies them before ingestion is queued. With no argument it uploads straight from `output/` and **writes no archive** (the protocol is per-file, so a tarball would be created only to be read back); give it a `.tar.zst`/`.tar.gz` to upload one an earlier CI step built. Endpoint from `--url` → `STEPPY_CLOUD_URL` → `cloud.url` in `config.yaml`; token from `--token` → `STEPPY_CLOUD_TOKEN` **only** (no config key, because that file is committed). `--attach <run-id>` uploads into an existing plane run instead of creating one — what `steppy ci run` will use.
- `steppy report [BUNDLE|DIR]` — render **one** run to a self-contained static site: outcomes, failure causes grouped by `_parallel/fingerprint`, the failing step named plus its timeline and captures, coverage buckets, a versioned `report.json` and a shields `badge.json`. Reads a live `output/` tree (no argument), a `.tar.zst`/`.tar.gz`, or an unpacked bundle dir — all three yield the same report. `--screenshots failed|all|none` (default `failed`), `-o/--output` (default `output/report`), `--badge-surface`, `--title`, `--force`, `--dry-run`, `--json`, `--open`. **Exits 0 even for a failing run** — it describes rendering; the verdict is in `totals.exit_code`.
- `steppy coverage refresh|report|merge|triage` — coverage-map commands: refresh the declared surface from `coverage.apis[].openapi` (URL or local path, + optional `coverage.sitemap`), print/export the gap report (tested / declared-unreached / discovered-uncovered buckets), re-merge a recorded run (rescue), set persisted `ui_testable|non_ui|unknown` triage flags. `report` also takes `--badge <path>` / `--badge-surface endpoints|routes|all` for the shields endpoint JSON.
- `steppy init --ci` / `--ci-gitlab` — scaffold `.github/workflows/steppy.yml` and/or `.gitlab-ci.yml`. Separate booleans on purpose: `--ci` is one people already type, so it cannot grow a value. Both carry a report step + artifact upload and a **commented** Pages job.
- `steppy init --app-dir DIR` — also install the app-side skill (`steppy-app-tours`) into the app's repository. `init` is safe to re-run, which is also how a hand-set-up project adopts the scaffold: it merges `.steppy/scaffold.json` (keeping the recorded `steppy_version`) instead of replacing it, and leaves the starter scenario out when `scenarios/` already holds some.
- `npm --prefix packages/player install && npm --prefix packages/player run build` — required once before any `steppy build` for a project that uses `modes: ['interactive']` or `modes: ['video']`. Produces four bundles under `packages/player/dist/` — the ESM `<steppy-guide>` player, the legacy cursor IIFE, the video-renderer IIFE, and the in-app tour overlay `steppy-tour.js` (+ `dist/types/` declarations); copy the **first three** to `src/steppy/_player_bundle/` to vendor them for the wheel (CI does this on release). The tour overlay is never vendored: it is meant for apps through npm (`@steppy/player/tour`, on npm at the `steppy-dev` version; a built checkout or its `npm pack` tarball only for unreleased changes). `npm --prefix packages/player run size:tour` checks its size budget; `npm --prefix packages/player run check:pack` fails when `package.json` (`main`/`types`/`exports`/`typesVersions`) points at a file `npm pack` would not ship.
- `npm --prefix packages/player test` — Vitest suite for the player: schema validation, animator math, component state machine, Python↔TS manifest bridge, the shared `src/ui/` modules (parity oracles against the pre-extraction guide code), and the tour overlay (engine, validator, loader, resolver, tracker, host in happy-dom).
- `STEPPY_TOUR_E2E=1 python -m pytest tests/integration/test_tour_replay_it.py tests/integration/test_tour_player_it.py -q` — in-app tours in Chromium (needs the player build and `playwright install chromium`); the `tour-e2e` CI job runs exactly this.
- `npm --prefix packages/angular ci && npm --prefix packages/angular test && npm --prefix packages/angular run build` — the Angular tour adapter `@steppy/angular`: a zoneless Vitest suite then a zone.js one (`ng test --configuration zone`) through the Angular CLI's `@angular/build:unit-test` builder, then ng-packagr into `packages/angular/dist/` (publish **`dist/`**, never the folder). Needs the player built first (it type-checks against `@steppy/player/tour`'s declarations).
- `STEPPY_TOUR_ANGULAR_E2E=1 python -m pytest tests/integration/test_tour_angular_it.py -q` — in-app tours in the Angular + PrimeNG + ngx-translate demo (`fixtures/tour-demo-angular/app`, built with `npm --prefix fixtures/tour-demo-angular/app ci && npm --prefix fixtures/tour-demo-angular/app run build` after the player and the adapter); the `tour-angular-e2e` CI job runs exactly this.

## Architecture

- `src/steppy/` — package source (models, parser, generator, cli, auth, config, guide, build)
- **The distribution is `steppy-dev`**, because `steppy` on PyPI is an unrelated project; the import package, the command and every other `steppy` name stay as they are. pip reads a name in two spellings, `steppy-dev[extras]` and `steppy-dev @ git+…`, so every install hint, CI template and requirement line uses `steppy-dev` (a bare `steppy` there installs the other project, or fails with pip's "inconsistent name" error). Code that asks `importlib.metadata` about the installed package uses `steppy.DISTRIBUTION`. Guard: `tests/test_distribution_name.py`.
- `templates/` — Jinja2 templates (user-customizable, takes priority). Resolution is one rule for every command
  (`generate`/`guide`/`build`), owned by `src/steppy/_templating.py`: an explicit `templates_dir` (**error** if it
  does not exist — silently shipping bundled templates would drop the whole override) → `<project_root>/templates`
  → bundled. Subdirectory-only overrides (`templates/static/…`, `templates/angular/…`) count; no top-level `*.j2`
  is required. Guard: `tests/test_template_precedence.py`.
- `src/steppy/templates/` — bundled fallback templates, **generated** from `templates/` at build time by `hatch_build.py` (gitignored; never edit or commit — edit `templates/` instead)
- `skills/` — packaged Claude skills that `steppy init` installs into a project's `.claude/skills/`, split by **job** rather than by subsystem: `steppy-scenario-author` (grammar, guides, build, PDF, video, in-app tour annotations and diagnostics), `steppy-template` (styling — guides, player, the tour overlay, print, and the run report's own stylesheet), `steppy-ci-report` (CI, `steppy report`, Pages, the coverage map and badge, tour replays and `tours --check`), `steppy-app-tours` (wiring tours into the **app's** code: serving the files, the Angular adapter, plain JS/React/Vue, test-ids, CSP). Adding one means adding its name to `SKILL_NAMES` in `init_cli.py` — that tuple drives the install, `steppy update`'s refresh, and its install of skills shipped after a project was scaffolded. A skill whose code lives in the app also goes in `APP_SKILL_NAMES`: `steppy init --app-dir DIR` installs those into the app's repository and records them in the project's manifest as `../<app>/…` paths, which `update_cli._skill_path` classifies by their last four parts. `LEGACY_SKILLS` names the folders people copied in by hand before skills were packaged; they were never in a manifest, so both commands only report them. `tests/test_skills_sync.py` fails when a visible command, a tour diagnostic code, or the overlay's/adapter's public API grows without the skills. Canonical source; `src/steppy/skills/` is the **generated** gitignored bundled copy (same `hatch_build.py` hook + `force-include` as templates). Keep client/private domain out — `tests/test_skills_neutralized.py` enforces it for the skills, and `tests/test_no_private_names.py` for every published file. Both read the terms from `private-terms.txt` (gitignored, one regex per line, see `tests/_private_terms.py`) and skip without it: no list of them, plain or hashed, is ever committed. Examples use the neutral `editor`/`reviewer`/`customer`/`invoice`/`product` domain.
- `scenarios/*.md` — Markdown scenario files with YAML frontmatter (canonical examples live here, not `examples/`)
- `seed/` — seed scripts run via subprocess before/after tests
- `tests/` — unit tests; `tests/e2e/` is generated output (gitignored)
- `output/screenshots/<scenario>/step-NN.png` + `step-NN.json` — captured during test runs; the JSON sidecar carries viewport + target bbox metadata consumed by `guide.py` to animate the cursor in HTML guides. Multi-frame fill-form emits `step-NN-a.png`, `step-NN-b.png`, … one per viewport slice.
- `src/steppy/coordinator.py`, `src/steppy/worker.py`, `src/steppy/_parallel/` — parallel-mode code, **lazy-imported only**. Single-worker path (`steppy run` and `--workers 1`) loads none of these. The worker image builds from the repo-root `Dockerfile` on a source checkout, or from the wheel-bundled `src/steppy/_docker/Dockerfile.installed` when steppy was pip-installed with no checkout present (see the parallel-execution pattern below).
- `src/steppy/coverage/` — coverage-map code (store, normalize, sourcemap, merge, manifest, gaps, report), **lazy-imported only** from `--coverage` post-run merge and the `steppy coverage` commands (guard: `tests/test_no_coverage_import_on_default_path.py`). Raw run records land in `output/coverage/raw/<run_id>/`; the persistent sqlite map lives at `.steppy/coverage.db` (outside `output/` so cleanup never wipes manual triage flags; `.steppy/` is gitignored).
- `src/steppy/video.py` — narrated-video renderer (`--video`), **lazy-imported only** and a **leaf module** (stdlib + `models` + `_player_bundle`; playwright imported inside `render_videos`; never imports `steppy.tts`). Drives `packages/player/src/video/` frame by frame over CDP and pipes JPEG stills to ffmpeg. Guard: `tests/test_no_video_import_on_default_path.py`. Rendered videos are content-addressed in `.steppy/video-cache/` (outside `output/`, which `build_all` rmtrees every run).
- `src/steppy/tts/` — text-to-speech provider layer for video narration (`types`, `presets`, `registry`, `cache`, `track`, `providers/`), **lazy-imported only**. One generic HTTP engine + a pure-data vendor registry, so `video.tts.provider` is the only thing that changes between engines. `presets.py` must stay httpx-free — it sits on an import path reaching the default CLI path.
- `src/steppy/video_cli.py` — `steppy video check` / `steppy video cache`, a leaf CLI module registered via `register_video(app)` (same shape as `register_flaky`). The cache mechanics live in `src/steppy/video_cache.py`, a **stdlib-only leaf** importing nothing from `steppy` (same split as `history.py`/`flaky_cli.py`) — `scan`/`stats`/`prune`/`sweep_scratch`/`clear`, driven by the `SIDECARS` table that says which companions travel with a `.mp4` or a `.wav`.
- `src/steppy/captures.py` — **stdlib-only leaf** owning the capture-path grammar in *both* directions: `step_stem` / `_has_captures` (moved out of `guide.py`, which imports them back, so `from .guide import step_stem` still resolves) plus the inverse `parse_step_stem` / `classify_capture_path`, and `sanitise_nodeid`. Also owns the grammar's **root**: `resolve_output_dir` + `DEFAULT_SCREENSHOTS_DIR` / `DEFAULT_GUIDES_DIR` (see the `config.output` pattern below). Never re-derive `step-NN[-frame]`, the locale/layout directory shape, or `output/screenshots` anywhere else — that is the FLAWS §4.1 rule applied to a grammar rather than a template.
- `src/steppy/locales.py` — **stdlib-only leaf** owning the BCP-47 tag grammar (`LocaleSyntaxError` / `normalize_locale` / `base_language` / `og_locale`), imported by `build_models.py` on the eager path like `exclusive.py` is by `models.py`. The whole module exists to keep **two forms of a locale** from being confused: the *authored* tag is an identity in three systems Steppy does not own — capture directories written by a different config file (`config.yaml`'s `locales`, or `steppy run --locales`, neither validated), the host app's ngx-translate `currentLang`, and every `LocalizedText` / `guide-text:` key — so it is **never rewritten**; the *normalized* tag serves only `hreflang`, `<html lang>` and `og:locale`, and lives in exactly one place, `BuildAssembler.html_lang`. The 2-3-letter bound on the language subtag is a correctness control, not style: it makes `index`, `video`, `interactive` and `x-default` unrepresentable as locales, and the first two are live collisions today (`<slug>/video.html` sits beside `<slug>/<locale>.html` and `_write_file` overwrites silently). `con` (Cofán) is rejected for the `exclusive.py` reason — `con.html` cannot exist on Windows — and the message offers `con-EC`.
  - **Both sides validate now.** `validate_locale_tag` is the shared pydantic-facing raiser: `models.SteppyConfig` (config.yaml's `locales`/`default_locale`) and `build_models.BuildConfig` both call it, and `selection.resolve_locales` (`steppy run/rerun --locales`) plus `steppy guide --locale` raise their own flavours. Every one of those becomes a screenshot directory segment the *other* side reads back, so an unchecked entry only defers the failure somewhere it cannot be explained. **`--layouts` is still unvalidated** and `tests/test_layout_fixes.py` positively pins that an unknown one round-trips — changing it is its own decision.
  - **`base_language` is byte-mirrored** as `_base_language` in `templates/conftest.py.j2` (guard: `tests/test_conftest_locale_mirror.py`), because the generated suite is standalone and still has to resolve a regional locale's i18n value. Three consumers share the rule — `pick_locale`, `GuideText.get` and `_apply_locale_init_script` — and the query is always *truncated*, never widened: `fr` must not match a map declaring only `fr-BE`. Before that, a regional build was a hard `ValueError` on the guide path, silent nulls on the interactive-manifest path, and on the capture side a silent skip that captured the app in its **default language** while filing the screenshots under the regional directory.
- `src/steppy/sitemap.py` — **stdlib-only leaf** owning `sitemap.xml` serialisation. See the SEO bullet under Patterns for the three ElementTree constraints that shape it and why the module is not justified by escaping alone.
- `src/steppy/exclusive.py` — **stdlib-only leaf** owning the exclusion-group grammar (`ExclusiveGroupSyntaxError` / `normalize_group_name`, shaped like `assertions` and `durations`, which `models.py` imports the same way) **and** the partition that collapses each group into one queue `Task`. Both halves live here for the same reason `captures.py` owns its path grammar in both directions: the name becomes a filename, so validating it and building the task id must not drift. Imports nothing from `steppy`, so `models.py` can import it on the eager CLI path without tripping the no-parallel-import guard.
- `src/steppy/runmeta.py` — **stdlib-only leaf** owning run identity (`new_run_id`, sortable) and the `--bundle` artifact layout (`output/events/<run-id>/`, `output/junit/<run-id>/`, `output/.steppy-run.json`). Shared by `cli`, `coordinator` and `bundle`, two of which are lazy-imported from the third — a common home is what avoids the import cycle.
- `src/steppy/contracts/` — versioned **wire** contracts: the results-bundle manifest (`bundle.py`, v1) and the run-report view model (`report.py`, v1). `extra="allow"`, deliberately inverting `models.py`'s `extra="forbid"`: config protects a hand-written file where a typo must fail loudly, a wire format needs the opposite. `contracts/bundle-manifest.schema.json` and `contracts/report.schema.json` at the repo root are generated from these models and drift-guarded by `tests/test_bundle_schema.py` / `tests/test_report_schema.py`, exactly like `steppy-config.schema.json`. Only `bundle` is re-exported from `contracts/__init__.py` — both modules define `accepts`/`schema_json`, so flattening them would collide. Neither file carries a render-time clock: the run's own `created_at` is the only timestamp, which is what makes both byte-reproducible for an unchanged run and therefore diffable in CI.
- `src/steppy/bundle/` + `src/steppy/bundle_cli.py` — the results-bundle producer, **lazy-imported only** (guard: `tests/test_no_bundle_import_on_default_path.py`). Split by concern: `hashing`, `classify` (path → `BundleFile`, pure), `results` (junit + events → `tests[]`), `manifest` (walk, budget, `truncated`), `archive` (deterministic tar + zstd/gzip dispatch), `create` (orchestration — `plan_bundle` decides a bundle, `archive_members` maps each manifest entry back to its bytes, `create_bundle` is the two plus a tar).
- `src/steppy/report/` + `src/steppy/report_cli.py` — the run-report site, **lazy-imported only** (guard: `tests/test_no_report_import_on_default_path.py`, which also re-asserts that `tarfile` stays off the default path — a new eagerly-imported CLI module is exactly how that regresses). Split by concern: `source` (three inputs → one `ReportSource` with a single `fetch(into=, texts=)`), `model` (**jinja2-free on purpose** — this is the module a control plane imports; importing a renderer alongside it would defeat the split), `assets` (policy, sanitised destinations, sha256 dedupe), `coverage_source` (the four tiers), `render` (jinja2, `autoescape=True`), `build` (orchestration + `ReportError`). Templates live in `templates/report/`. **The report never parses a path** — `bundle/classify.py` already stamped `scenario/locale/layout/step/frame` onto every manifest row, so the whole thing is a manifest transform (FLAWS §4.1 applied to the manifest). Two read-side rules: destinations are computed from validated components, never from a manifest path (an arcname in a downloaded bundle is attacker-controlled and streaming tar members skips Python's extraction filters), and no absolute path reaches `report.json` or the page footer, both of which get published.
- `src/steppy/migrate/` + `src/steppy/migrate_cli.py` — the `custom`-block codemod, **lazy-imported only** (guard: `tests/test_no_migrate_import_on_default_path.py`). Split by concern: `rules` (statement → step dict, pure; all-or-nothing per block), `plan` (file → rewrites, plus the two neighbour-aware folds — a trailing sleep becomes the previous step's `wait_after:`, a bare load-state wait folds into the `navigate` before it), `verify` (what can honestly be proven: the code parses, no string literal is lost, and every Playwright call survives up to a declared substitution — **not** textual equality, which would reject exactly the rewrites worth making), `apply` (render through the *real* generator, then write).
- `src/steppy/coverage/triage.py` — **stdlib-only leaf** owning the `coverage.non_ui` overlay, applied *between* `store.read_map` and `gaps.compute_gaps`. Not in either: `read_map`/`dump_canonical` are byte-compared by the store tests and describe what is *persisted*, and `compute_gaps` is pure bucket math. ## Patterns

- Pydantic models use `class Config: extra = "forbid"` (legacy style, not ConfigDict)
- Comment conventions (enforced partially by ruff; the prose parts by review): full-line sentence comments start with a capital letter and read as prose; `# ── Title ───…` box-drawing banners are for major file sections only; two spaces before an inline `#`; TODOs follow flake8-todos format (`TODO(author): description` + issue link — ruff `TD` enforces this; no linter exists for capitalization/banner prose style, that's a review concern)
- Parser passes frontmatter metadata as `**kwargs` to Pydantic — add validators to models, not parser logic
- New frontmatter blocks need only a pydantic model; `frontmatter.load` already returns nested dicts
- Step-level nested blocks are YAML, at most two levels deep (`guide-text:` / `tour-text:` → `fr:` → `title:`/`text:`); deeper nesting is not part of the grammar
- Scenario.seed uses a normalizing `field_validator(mode="before")` to accept both `str` and `dict` forms
- **Single template source (FLAWS §4.1):** edit templates in the repo-root `templates/` tree ONLY. The bundled `src/steppy/templates/` copy (the wheel's fallback, and what the runtime loads when a project has no local `templates/`) is **generated** from the root tree by the hatchling build hook (`hatch_build.py`) on every build — for the wheel, sdist, and `pip install -e .`. It is gitignored; never edit or commit it. Older per-feature notes below that say "mirror across BOTH trees" now mean simply "edit `templates/` — the bundled copy regenerates automatically." Downstream projects customize the root `templates/` copy.
- **`steppy build` pipeline**: reads a TS config (`steppy.guide.config.ts`) via `npx tsx` subprocess, reuses `GuideAssembler.prepare_guide_steps()` for HTML generation, then dispatches on the config's `target` field (default `static`). `target: 'angular'` writes role-scoped Angular 21 standalone components + a per-role `<role>.routes.ts`, a `<role>.nav.json` (translation-key references, no inlined `LocalizedText`), and an `i18n/<role>/<locale>.json` per configured locale to `outputDir`. Screenshots are copied to the configured `assetsDir`; image URLs in the rendered HTML fragments are absolute `/assets/<role>/<slug>/[<locale>/][<layout>/]step-NN.png` — the host app exports `assetsDir`'s contents into `public/assets/<role>/` so the URLs resolve. The host owns locale state via `@ngx-translate/core` (the generated components inject `TranslateService` and resolve `<ROLE>.guides.<slug>.title` etc. through the translate pipe). `target: 'static'` writes a self-contained static site to `outputDir` (full HTML pages at `<slug>/<locale>.html`, an `index.html`, `manifest.json`, a shared `assets/guides.css`, `.nojekyll`) with screenshots co-located under `outputDir/assets/<slug>/` — `assetsDir` is ignored, and screenshot URLs are relative so the build works on any deploy root. **Both targets support `modes: ['interactive']`** — Angular emits a real `<slug>-interactive.component.ts` that mounts `<steppy-guide>` and bridges ngx-translate's locale into it; static emits a self-contained `<slug>/interactive.html` page that loads the player bundle and the manifest with relative URLs. See `build.py`, `build_models.py`, `templates/angular/`, and `templates/static/`.
- **Interactive guide mode**: `modes: ['interactive']` on a guide produces a `guide.json` manifest plus a host (Angular component or HTML page) that mounts the Lit `<steppy-guide>` web component shipped from `packages/player/`. The manifest is built by `GuideAssembler.prepare_interactive_manifest()` (in `src/steppy/guide.py`), which calls the existing `prepare_guide_steps()` once per (locale, layout) and merges into the shape codified by `packages/player/src/manifest/schema.ts`. **Both modes can coexist** on a single guide — Angular shows them as a mode toggle via a PrimeNG `SelectButton`; static emits both `<slug>/<locale>.html` (stepbystep) and `<slug>/interactive.html` (interactive) alongside each other. Build emits: per-guide `guide.json` (Angular: at `assetsDir/<slug>/guide.json`; static: at `outputDir/<slug>/guide.json`), a `steppy-player.js` ESM bundle copied once-per-build into the assets dir, and target-specific host code. Stage 4 lifted the historical static-target rejection of interactive mode — both targets now use the same `<steppy-guide>` component.
- **Layout twin-branch pattern + per-capture `content`**: a scenario may author one logical step **twice** — once per layout — when the DOM path differs (`layouts: [desktop]` on a sidebar click, `layouts: [mobile]` on the drawer twin). The manifest merges pairs by list **position**, not by scenario step number, so complementary `original_index` values are expected and are *not* an error; what it cannot express is a divergent step **count** per layout, which stays fatal (`prepare_interactive_manifest`'s one remaining coverage guard — the layout-invariant `action`/`interactive`/`screenshotWhen`/`waitAfter` fields all come from the canonical `default_layout` branch, and a twin disagreeing on `action` warns while one disagreeing on cursor presence still raises). Because twins usually reword their instruction ("click the row of the table" vs "tap the card"), `captures[locale][layout]` carries an optional `content: {title, text, subtitle}` override beside the frames it describes — plain strings, since the bag is already locale-scoped. It is **atomic** (all three or none): a partial override would pair one layout's heading with another's body in the sidebar template. It is emitted **only when it differs from the step-level triple**, so a guide with no twins — and every single-layout or layout-less build, where canonical *is* the only layout — stays byte-identical, which is also what keeps `video.job_fingerprint` (it hashes the whole manifest) from churning the render cache. Resolution lives in **one** place, `packages/player/src/manifest/content.ts` (`resolveStepContent` + `captureLayoutKey`), imported by `steppy-guide.ts` (`_captureFor`/`_contentFor` → `_renderStage` + `_buildStepViews`, which maps *every* step so the whole timeline re-labels on a layout toggle) and by `video/{timeline,stage}.ts`. **The invariant is that content and frame come from the same `Capture` object** — read them under different layout keys and a viewer gets one layout's instructions over another's screenshot. Manifest version went `1.0` → `1.1`; `parse.ts` gates on the major only, but `Capture` is a strict Zod object, so a 1.1 manifest fed to a stale vendored bundle fails validation outright — emitter and `_player_bundle` must always ship together.
- **Presentation templates (player `overlay` | `sidebar` | `inline`)**: the interactive `<steppy-guide>` player separates engine from presentation. `template` is a runtime-switchable, persisted viewer setting resolved **attr → `localStorage['steppy:active-template']` → manifest `defaultTemplate` → `overlay`**. Engine logic (step state, cursor animation, hotspot/tooltip placement, nav, keyboard, i18n, locale/layout) stays on the component; each template is a pure `render(ctx: TemplateContext)` + `styles` in `packages/player/src/templates/{overlay,sidebar,inline}.ts` (registry + `ALL_TEMPLATES`/`isTemplateId` in `index.ts`; shared tokens/stage/chrome CSS in `base-styles.ts`; shared chrome fragments in `controls.ts`). The component builds an immutable `TemplateContext` (`templates/types.ts`) and exposes the live stage via a `renderStage()` thunk. **Switching templates preserves step/locale/layout/highlight (no reset)** — Lit recreates the `.steppy-stage` on switch, re-bound in `updated()`→`_reattachStage` (`animator.setStage` + re-observe + recompute); do **not** rely on `keyed` (it breaks happy-dom `querySelector`). Forward nav (`Next`/`→`) resolves the pending interactive wait and advances in **all** templates (`next()`→`_confirmHotspotClick`). New manifest fields are additive + `.optional()` (back-compat): per-step `title` (sidebar heading; player falls back to `text`) and top-level `defaultTemplate`. Threaded `GuideEntry.template`/`BuildConfig.default_template` (build_models.py) → `prepare_interactive_manifest(default_template=...)` + per-step `title_per_locale` from `gc.title` (guide.py) → both host trees set `template="{{ default_template }}"`. The persist guard skips the initial `null` (else it pins `overlay` and starves the manifest default). Add a chrome string: extend `UiStrings` + all four locales in `i18n/ui-strings.ts`. Touch points when adding a template id: `TEMPLATE_MODES` (schema.ts `.strict()`), `TemplateMode` (build_models.py + packages/steppy/index.ts), `ALL_TEMPLATES`/`TEMPLATES` (index.ts). See [packages/player/README.md](packages/player/README.md). **Sidebar's layout is token-driven and its rail is capped**: the rail has a `max-height` and the *timeline* is what scrolls (`min-height: 0` is load-bearing — a flex item won't shrink below its content without it, and the cap is inert), sticky sits on the **rail** not the preview (a tall mobile capture as the sticky element would put its own bottom out of reach), and `--steppy-rail-width` / `--steppy-rail-max-height` / `--steppy-sidebar-offset` / `--steppy-rail-max-height-narrow` exist because the shadow DOM exposes no `part=` — an embedded host (the Angular target, whose chrome sits above the player) must override the `100vh` cap. Two rules of the road for this file: sidebar duplicates its collapse rule in **both** a `@container` and a `@media` block, so every responsive rule needs both copies; and CSS comments inside the `css` tagged template must not use the repo's ``double-backtick`` prose convention — a backtick there terminates the literal (the failure reads `css(...) is not a function`).
- **Cursor JS is a single canonical TS source**: `packages/player/src/cursor/animator.ts` is built into both an ESM bundle (consumed by the Lit player) and an IIFE bundle (`steppy-cursor-legacy.js`) that drop-in replaces the inline cursor JS in `templates/static/cursor.js.j2` (rendered via `{{ cursor_iife | safe }}` from `get_legacy_cursor_iife()`) and the cursor `<script>` block in `templates/guide.html.j2`. Animation math (`scaleBbox`, `easeInOut`, Bezier control points, travel duration) and the state machine (idle → travel → pre_action → action → post_action) live in one place; both consumers import them.
- **Angular stepbystep cursor**: the Angular target injects the guide HTML via `[innerHTML]`, and the browser never executes `<script>` inserted that way — so the cursor driver can't ship inside the fragment. Instead `src/steppy/templates/angular/component.ts.j2` loads the **same** `steppy-cursor-legacy.js` IIFE once per page (copied to `assetsDir/steppy-cursor.js` by `_copy_cursor_bundle`, served at `/assets/<role>/steppy-cursor.js`, like the interactive `steppy-player.js`) and calls the IIFE's exposed `window.__STEPPY_CURSOR__.mount(root, steps, timings)` over the component's own DOM after every render. The legacy IIFE (`packages/player/src/cursor/legacy-iife.ts`) gained `mount()` (scoped, returns a disposer) + the `window.__STEPPY_CURSOR__` global, and its DOMContentLoaded auto-init is now **guarded on the `__STEPPY_STEPS__` globals** so it stays a no-op in the SPA (the static templates still set those globals, so they auto-init unchanged). Per-step frame data (`{index, frames:[{viewport, cursor}]}`) + timings are baked into `angular/content.ts.j2` as `STEPS`/`TIMINGS` (keyed `[locale][layout]`); the component's `effect()` re-mounts whenever `selectedLocale`/`selectedLayout`/`selectedMode` swaps the injected DOM, disposing the prior mount via the effect cleanup. Rebuild + re-vendor the IIFE after editing `legacy-iife.ts` (see `_player_bundle`).
- **Fragment template `include_styles`**: [guide.fragment.html.j2](templates/guide.fragment.html.j2) wraps its inline `<style>` block in `{% if include_styles | default(true) %}` so the static page template can render it with `include_styles=false` and link to the shared `assets/guides.css` instead. Default-true preserves the standalone `steppy guide` and Angular consumers.
- `packages/steppy/` contains the npm types package (`defineGuideConfig`) that target Angular apps import for config type-checking. The target app references it via `"steppy": "file:../../packages/steppy"` in devDependencies.
- `packages/react/` (`@steppy/react`) and `packages/vue/` (`@steppy/vue`) are **thin, starter** framework wrappers around the `<steppy-guide>` web component: they side-effect `import '@steppy/player'` to register the element, reflect declarative props onto attributes/properties, and surface the seven `steppy:*` events as callbacks/emits. React uses `forwardRef` + imperative `setAttribute` in a `useEffect` (robust across React 17/18/19 custom-element prop handling); Vue uses a render-fn `defineComponent` (`h('steppy-guide', …)`) so no host `isCustomElement` config is needed. Each has a vite lib build (`external` React/Vue + `@steppy/player`) + a `tsc -p tsconfig.build.json` d.ts step, one happy-dom Vitest smoke test, and a `declare module '@steppy/player'` shim (written before the player shipped declarations; `dist/types/index.d.ts` exists now, so the shim can go). They're deliberately minimal — to be hardened when Steppy is implemented on OSS React/Vue projects. Version-locked with the rest via `test_versions_aligned.py`.
- `packages/angular/` (`@steppy/angular`) is the **in-app tour adapter** for Angular 20–22 (built and tested on 21 in CI; 20.0, 20.3 and 22.2 checked once in throwaway apps, see `docs/design/in-app-tours.md` §11): `provideSteppyTours()`, `<steppy-tours>` (placed once in the shell), the root `SteppyTours` service and the `steppyTourStart` directive. Five things are load-bearing. (a) **The overlay is only ever a dynamic `import('@steppy/player/tour')`** (`OVERLAY_LOADER` in `src/overlay.ts`, the test seam): every other reference is `import type`, because the module touches `HTMLElement` at load — guard: `tests/test_angular_adapter_sync.py`, which also pins the tag, the six event names and the `applyProps` writes against the overlay. (b) **The element is created imperatively and put on the page before the module defines it** (from `afterNextRender`, outside the zone): Lit keeps properties set before its upgrade, the six listeners catch a resumed tour's `tour-start`, and the generated replay — which waits for `customElements.whenDefined` and then `querySelector`s the host — finds it. No template binding, no `CUSTOM_ELEMENTS_SCHEMA` anywhere. (c) **`navigate` re-enters the zone** (`createNavigate` → `zone.run`), or a zone.js app never renders the routed page; the router bridge reads the outcome from `router.url`, because `navigateByUrl` resolves `false` for both a refused navigation and the current URL, and `true` for a guard redirect — a refusal or redirect rejects, which the overlay reports as `entry-params` at once. With no `ROUTES` provided it returns `null` (the overlay's full navigation). (d) **Everything else the overlay does stays outside the zone** (`start`/`stop`/`next`, property writes, the `readyTimeout` timer); events and outputs come back in through `zone.run`. (e) **Destroying `<steppy-tours>` suspends rather than dismisses** a running tour (the overlay's teardown keeps the resume record). One `package.json` is both the CLI workspace and the library manifest (no `src/lib/`: the root `.gitignore` ignores `lib/`); `@steppy/player` is an exact-version peer and a `file:../player` dev dependency. `fixtures/tour-demo-angular/app` is the plain demo rebuilt in Angular + PrimeNG + ngx-translate with the **same routes and test-ids**, so `fixtures/tour-demo/project` drives both apps unchanged; it consumes `packages/angular/dist` and `packages/player` through `file:` links, which is why its build sets `preserveSymlinks` (otherwise a second `@angular/core` loads from `packages/angular/node_modules`, NG0203). `fixtures/tour-demo/serve.py` serves it with `--app-dir` and `--style-src "'unsafe-inline'"` (Angular and PrimeNG inject `<style>`; scripts stay `'self'`).
- `fixtures/demo-guide/` is a minimal test project with dummy scenarios + screenshots for exercising `steppy build` end-to-end.
- **Brand (`docs/brand/`)**: the mark (a checked box) and an app icon as SVGs — no wordmark — and the palette Pin `#15332A` / Lichen `#E4E9E1` / Balise `#D2561A` / Granite `#5B6B64`. The run report (`templates/report/`) carries the mark, favicon and palette; the guide templates stay neutral on purpose (they document the user's app). Balise is never text colour as-is (4.0:1): links use `#A8410E` light / `#F09A6A` dark.
- Seed scripts are idempotent and called via subprocess (`python seed/<name>.py`)
- **Cursor bbox timing invariant**: for the HTML guide cursor to land on the right pixel, the target bbox must be captured from the same scroll state the screenshot sees. `_safe_bbox_scrolled` in `conftest.py.j2` scrolls the element into view before measuring, which matches what Playwright's action auto-scroll would do anyway. Capturing a bbox before that scroll produces stale (often off-viewport) coordinates.
- **Multi-frame fill-form**: tall forms are captured across multiple screenshots (`step-NN-a`, `-b`, …) by `take_fillform_frames`, which iteratively scrolls each uncovered field into view until every field is in-viewport in at least one frame. `guide.py` then animates each field in the **first** frame where it appears (tracked via an `already_animated` selector set) so no field is visited twice.
- **`screenshot-when: before`**: on interactive actions (`click`, `fill`, `fill-form`, `select`, `hover`, `upload`, `custom`), the scenario may opt into pre-action capture — required when the action navigates away or unmounts the target. Default is `after`.
- **Adding a new action** (canonical checklist — the per-action notes below only list what is *extra*):
  1. `VALID_ACTIONS` (models.py) — one entry. It is a module-level frozenset, not rebuilt per step.
  2. `_REQUIRED_FIELDS` (models.py) — one row per required field, `(attr, description)`. This produces
     `"<action> action requires '<attr>' (<description>)"`. **Most actions need nothing else in models.py** —
     add a `@model_validator` only for a rule a table cannot express (mutual exclusion, a format regex,
     a cross-field shape). Any new optional fields go on `Step` as usual.
  3. `templates/test_scenario.py.j2` — one `{% elif step.action == "..." %}` block. Use the `shot(step, action, when, …)`
     macro for the before/after captures and `disambig_locator(...)` if the action resolves a selector; do **not**
     hand-roll the screenshot scaffold. Edit only this tree — `src/steppy/templates/` is generated.
  4. `_SIMPLE_CURSOR` (guide.py) — one row `(kind, value_attr|None)`, unless the action's cursor is genuinely
     multi-target (only `fill-form` is). Add to `_NO_SELECTOR_CURSOR` if the target is resolved imperatively,
     or to `_HIDDEN_CURSOR_ACTIONS` if it is non-visual and should show no cursor at all. Every action must
     appear in exactly one of those — `tests/test_action_enum_sync.py` fails otherwise. Skipping this is
     silent: the step renders with `cursor: null` and `interactive: false` and every suite stays green.
  5. `ManifestAction` enum (packages/player/src/manifest/schema.ts) — the schema is `.strict()`, so an action
     missing here makes the player reject the **whole** manifest and the interactive guide renders nothing.
     `tests/test_action_enum_sync.py` fails if you forget. Then rebuild + re-vendor the player bundle.
  6. `_ACTION_BODIES` (tests/test_step_events_codegen.py) — one minimal valid step body. The per-step event
     markers are emitted by the loop rather than per action, so a new action inherits them for free; this
     table is what proves it, because the whitespace bug it guards against fired for exactly one action and
     was invisible for the rest. `test_action_bodies_cover_every_action` fails if you forget.
  7. `ACTION_TOUR_KIND` (`src/steppy/tours/actions.py`) — one row saying what the action becomes in an in-app
     tour (`click` / `change` / `input` / `fill-form` / `upload` / `check` / `cursor` / `unguided` / `navigation` /
     `skip`), and, if it can be a tour step, its replayable-advance family in `_REPLAYABLE`.
     `tests/test_tour_action_table.py` fails if a `VALID_ACTIONS` member has no row.

- **In-app tours (`tours:` + `tour:`, see `docs/tours.md` and `docs/design/in-app-tours.md`).** Seven things are load-bearing. (a) **Off means byte-identical**: `tests/_codegen_snapshot.py` renders every scenario corpus plus a synthetic every-action matrix and compares sha256 manifests before/after a template change (run it from the repo root: `python -m tests._codegen_snapshot --out DIR`, then `--compare A B`); `generate_test_file` always passes `tour_replay` explicitly (an undefined template name resolves to Jinja's `missing` sentinel, and `tests/test_report_model.py` re-imports jinja2, which makes the compiled template compare it against a different sentinel). (b) **One step body**: the main loop and the replay both render the `step_body(step)` macro (`test_scenario.py.j2`), composed in Python by `generator._tour_section` like `_bracket_step`, so a replay performs exactly the scenario's action code (guard: `test_every_replayed_action_is_the_scenario_test_code`). (c) **The conftest block is appended, not woven in**: with tours on, an EOF block rebinds `_new_role_context` (kill-switch init script), `_coverage_stop_and_write` (replays write no coverage) and `pytest_collection_modifyitems` (`GUIDE_MODE` deselects replays) — callers look names up at call time; replays are recognised by the `_steppy_tour_role` function attribute.   - **`seo.lastmod` is opt-in and there is no `'auto'`**: unset ⇒ no `<lastmod>` ⇒ byte-reproducible. `auto` was rejected because `actions/checkout` stamps every file at clone time (so it reads as "now" forever), screenshots are not in git, and `test_deterministic_output` builds twice in one process from one `tmp_path` — it would pass while the real invariant broke. Same precedent as `_video_stamp`'s `date.today()` behind `options.stamp.enabled`. Validated by regex **then** `fromisoformat` (neither alone: `fromisoformat` accepts `20260914`, `2026-W12-1`, a space separator and a timezone-less time). `<changefreq>`/`<priority>` are not emitted — Google and Bing ignore them.
  - **Two of the emitted files are honoured only at the origin root**, and nothing about that is visible locally. `robots.txt` and the `_headers` sidecar both are; a GitHub Pages *project* site is served under `/<repo>/`, so a correct `seo.baseUrl` there carries a path and both land where nothing reads them — `_warn_root_only_files` says so at build time. Canonical links, `hreflang` and `sitemap.xml` are absolute and unaffected, as is the per-page robots meta.
  - **`_headers` exists because a PDF cannot carry a robots meta.** `handbook/<locale>.pdf` is Chromium printing a page that is deliberately `noindex`, and `<slug>/<locale>.pdf` competes with its own HTML the same way — so the published PDF was the only indexable form of both. Public mode noindexes `/*.pdf`, private mode `/*` (there, the per-page meta is the *only* other control and a PDF has none). Read by Netlify and Cloudflare Pages, **ignored by GitHub and GitLab Pages**, which are the two the shipped CI scaffolds target — the same bargain `.nojekyll` makes, and the docs say so rather than implying coverage. `TestSitemapInvariant` globs `*.html` and therefore cannot see a PDF at all, which is how this went unnoticed; `TestHeadersSidecar` walks `*.pdf` separately.
  - Touch points: `SeoConfig`/`SeoMode`/`GuideEntry.description`/`BuildConfig.locales` validators (build_models.py); `src/steppy/sitemap.py` + `src/steppy/locales.py`; the helpers and writers in build.py; the `templates/static/` partial; TS `SeoConfig` in **both** `packages/steppy/index.ts` and `index.d.ts` (hand-synced, guard: `tests/test_seo_config_sync.py`); **no player/schema change** (build-only — no bundle rebuild/re-vendor).

- **`STEPPY_NO_ASSERTS` / `--no-asserts`**: `steppy run --no-asserts` sets `STEPPY_NO_ASSERTS=1`; the generated `test_scenario.py` imports `SKIP_ASSERTS` from conftest and wraps every assertion in `if not SKIP_ASSERTS:`. `--guide` auto-enables it because text assertions (toasts, row-contains, etc.) are language-specific and would fail every non-default locale during multilingual capture.
- **Conditional steps (`only-in` / `layouts`)**: a step can carry `only-in: test` or `only-in: guide` to restrict which mode it runs in (default = both), and `layouts: [desktop, mobile]` to whitelist layouts. The CLI sets `STEPPY_GUIDE_MODE=1` for `--guide` runs; conftest's `_step_runs(only_in, layouts)` predicate centralises the rule (`only-in: test` skipped in guide mode; `only-in: guide` skipped outside). The layout filter only fires when a layout is **active** (`CURRENT_LAYOUT` is set, i.e. the run was parametrized via `STEPPY_LAYOUTS`) — when no layout is active (no layout parametrization set), the layout filter is ignored and the step runs at the default viewport. The test template wraps each filtered step's body in `if _step_runs(...)` via the `apply_step_guard` filter — unfiltered steps emit byte-identical to pre-feature output. `only-in: test` + `layouts: [mobile]` is a valid combination meaning "run only outside guide mode, only when the mobile layout is parametrized".
- **Scenario-level `layouts:` declaration (A.2)**: a scenario can declare `layouts: [desktop, mobile]` in **frontmatter** (distinct from the step-level `layouts:` above) to make responsive coverage a versioned property of the flow. Semantics (`_effective_run_layouts` in conftest): absent ⇒ byte-identical default; declared + plain `steppy run` ⇒ **authoritative** (the whole test parametrizes over the declared layouts even with no `--layouts`); declared + `--layouts`/`--guide` ⇒ **intersection** in run-selected order (so desktop-only scenarios stop producing phantom mobile captures); disjoint ⇒ the scenario is **silently deselected**. Mechanism: the generator bakes `SCENARIO_LAYOUTS = [...]|None` into each `test_<slug>.py` next to `SCENARIO` (`test_scenario.py.j2`, via `{% if %}`/`tojson` — **not** `pystr`, which stringifies a list); a `pytest_generate_tests` hook (conftest) owns the `(locale × layout)` parametrization of the role page fixtures (which therefore **dropped their own `params=`** — the idiomatic indirect pattern), reading the module's `SCENARIO_LAYOUTS` and intersecting with `LAYOUTS_FOR_RUN`. **Every role page fixture a test requests is bound under ONE `parametrize` call** so the roles move in lockstep. One call per fixture multiplies: a two-role scenario collected 4× instead of 2× under two layouts, and because `CURRENT_LOCALE`/`CURRENT_LAYOUT` are one global that every role fixture writes, a mixed item filed one role's desktop capture under the other's `mobile/` directory. Two details are load-bearing. First, a *single* fixture keeps the string-argname call, because pytest's `force_tuple` is what leaves `request.param` a bare `(locale, layout)`. Second, the multi-fixture call takes `ids=` as a list of strings, because an id callable is applied per argname and hyphen-joined (`fr-mobile-fr-mobile`). Guard: `tests/test_layout_fixes.py::TestMultiRoleLockstepCollection`; a `pytest_collection_modifyitems` hook deselects the disjoint case (the hook must **skip** `parametrize` when the effective set is empty — an empty `parametrize` + id callable crashes on pytest's empty-set sentinel). No CLI/env-var change (`STEPPY_LAYOUTS` stays the run-level CSV; baking is generate-time, intersection is conftest-time) → parallel path unaffected, byte-identical guard (`test_run_byte_identical.py`) still holds. Touch points: `Scenario.layouts` + `validate_layouts` (models.py, mirrors `Step.validate_layouts`); `validate_scenario_layouts` extended to the scenario level (parser.py; all three `cli.py` call sites already invoke it); `SCENARIO_LAYOUTS` bake + the three conftest additions (`_PAGE_FIXTURES`, `_effective_run_layouts`, the two hooks) in the canonical `templates/` tree only. Composes with step-level `layouts:`/`only-in:` (the parametrization narrows the layout set; `_step_runs` still gates individual steps within each layout).
- **PDF export (`--pdf` / `--handbook` on `guide` and `build`)**: Steppy lays out no PDF of its own — `src/steppy/pdf.py` (a leaf module; **playwright imported inside `render_pdfs`**, guarded by `tests/test_no_playwright_import_on_default_path.py`) prints the *already-generated* guide HTML through headless Chromium, so the `@media print` blocks in the templates ARE the PDF layout. Three invariants: (a) pages load over **`file://`** (`Path.as_uri()`) — guide HTML uses relative screenshot URLs, and `set_content` would resolve them against `about:blank` and blank every image; (b) `loading="lazy"` images are flipped to `eager` and awaited (`wait_for_function`, bounded by `pdf.timeout`) before printing — below-the-fold images are the classic empty-stage print bug — with a timeout that *warns and prints anyway*; (c) one browser/one page for the whole batch (a project is scenarios × locales × layouts). `print_background` defaults **true** (Playwright's own default is false, which would drop every step badge). Failures are per-job (`PdfResult`), never fatal; only a launch failure raises `PdfRenderError` (carrying the `playwright install chromium` hint). **Handbook** = `templates/guide.book.html.j2` — pre-rendered `guide.fragment.html.j2` fragments (`include_styles=false`) + the shared `static/guides.css` inlined through the same Jinja loader, so there is no fourth copy of the guide CSS; `steppy guide` writes `<role>-handbook.html` beside the per-guide pages (identical relative image URLs) and `steppy build` writes `handbook/<locale>.html` **one directory deep on purpose** so the `../assets/…` fragments are reusable verbatim. Print-CSS touch points are the usual three surfaces (`guide.html.j2`, `guide.fragment.html.j2`, `static/guides.css`): `print-color-adjust: exact`, `page-break-inside: avoid`, the `--steppy-print-max-image-height` token (Chromium cannot split an image, so an uncapped full-page capture is *clipped*), and — in `guides.css` only — hiding the site chrome, which is what lets `build --pdf` print the published page as-is. `--dry-run` records `planned` PDFs and never launches a browser; the Angular target rejects both flags.
- **Video guide mode (`modes: ['video']` + `--video` on `guide` and `build`)**: Steppy screen-records nothing. `packages/player/src/video/timeline.ts` lays the *interactive manifest* onto an absolute millisecond timeline whose state at any instant (`stateAt`) is a pure function of its inputs; `stage.ts` paints one instant per `seek(i)`; `src/steppy/video.py` (a **leaf module** — stdlib + `models` + `_player_bundle` only, **playwright imported inside `render_videos`**, and it never imports `steppy.tts`) drives that over CDP and pipes JPEG stills to ffmpeg. Load-bearing decisions: (a) **display scale is measured in the browser, never derived** — `.steppy-stage img` is `width:auto; max-width:100%`, so displayed width is `min(intrinsicPngWidth, stageWidth)` and `intrinsicPngWidth = captureSize.width × device_scale_factor`, a factor the manifest does not carry; since `travelDuration` consumes *display* distance, video duration also varies with `video.width`; (b) **no player-schema change** — the video consumes the manifest verbatim, `mode: z.literal('interactive')` names the *format* not the build modes, so `steppy-player.js` stays byte-identical; (c) **CSS animations and transitions are disabled and recomputed inline**, because `animation-delay` cannot scrub a `transition` (`.steppy-cursor` fades opacity that way) and `prefers-reduced-motion` would strip the rest — hence `reduced_motion="no-preference"` on `new_context()` and the `video-stage.test.ts` CSS-constants drift guard; the ripple is a 400 ms overlay independent of `action_ms` (hardcoded in `base-styles.ts`); (d) **ffmpeg's stderr goes to a temp file, never a pipe** — an undrained pipe fills, ffmpeg stops reading stdin, and the frame loop deadlocks silently; (e) progress is **step-discrete**, because a per-millisecond bar would make every frame dirty and destroy the dedup that carries the render budget. A separate third bundle `steppy-video.js` (IIFE, `window.__STEPPY_VIDEO__`, `emptyOutDir: false` in `vite.video.config.ts`) is inlined into a throwaway harness written *beside the guide page* (relative screenshot URLs resolve against the document; `fetch` on `file://` is blocked, so the manifest is inlined) and is **never copied into a build's output**. The renderer builds its **own** manifest with disk-relative URLs (`_build_video_manifest`), which is what lets the Angular target work at all — its published URLs are root-absolute. Caches live under `.steppy/` (`video-cache/`, `tts-cache/`, `voices/`) because `build_all` rmtrees `output/` every run. **`output/videos/` and `STEPPY_VIDEO` belong to `report.video`** (Playwright failure footage) — unrelated feature, do not reuse.
- **TTS provider injection (`video.tts`)**: one generic HTTP engine (`tts/providers/http.py`) plus a pure-data registry of vendor shapes (`tts/presets.py`), not a class per vendor — so adding ElevenLabs' successor is a dict row and an unsupported API needs only `video.tts.http` in YAML. Resolution cascade (`tts/registry.py`, mirroring `_parallel/image.py:resolve_build_inputs`): entry point `steppy.tts_providers` (lru_cached, lazy — `entry_points()` walks every installed distribution) → builtin (`none`/`piper`/`espeak`/`http`) → preset over the HTTP engine with explicit `video.tts.http.*` layered on top via `model_fields_set` (the `_PresetModel` rule) → error listing what *is* available. Placeholders are substituted on **parsed-JSON string leaves**, never on serialized JSON, so narration containing a brace cannot corrupt a request body. **`httpx` must stay out of module scope**: `TtsConfig` lives in `models.py` on the eager CLI path and `tests/test_no_playwright_import_on_default_path.py` forbids httpx transitively — hence `presets.py` is pure data and `import httpx` sits inside `synthesize`. **Piper is subprocessed, never imported** (piper1-gpl is GPL-3.0; arms-length use keeps it out of a permissive wheel, and it is deliberately not a `pyproject.toml` extra). The clip cache key includes the **engine version**, because a local engine's output shifts between builds and a stale clip's duration no longer matches the timeline it was rendered against; for the HTTP engine `version()` also folds in a hash of the resolved **request spec** (pre-substitution, so it carries `{api_key}` placeholders and never the secret — editing `video.tts.http.json` must re-synthesize, rotating a key must not). Narration runs *before* the browser opens (the timeline needs durations to size each step) but is *assembled* after (only the timeline knows each step's offset) — hence the injected `assemble_audio` callback on `render_videos`, which is also what keeps `video.py` free of `steppy.tts`. Both entry points share `tts.voice_jobs` / `tts.assemble_track`; `build.py` and `cli.py` held byte-identical copies of these and had already drifted on cache-path resolution.
- **Cache invariants for narration + video (all four are silent when broken):** (1) **Every cache write is atomic** — stage a sibling temp file and `os.replace` (`ClipCache.commit`/`staging_path`, `track.normalize`, `video._staging_path`). A lookup that only asks `is_file()` will serve a truncated artifact forever, so a Ctrl-C mid-encode is not a slow build, it is a permanently poisoned entry. (2) **A hit is validated, not trusted** — `track.is_intact_wav` compares the declared payload against the bytes on disk (a truncated write leaves the 44-byte header intact, so `getnframes()` still reports the *intended* length), and `video._cache_entry_is_usable` checks the `.meta` sidecar's recorded companion list. A bad entry is discarded and re-made, never raised. (3) **Cache dirs resolve through `captures.resolve_output_dir(project_root, …)`** — the config values are bare relative paths, so `synthesize_steps(cache_root=…)` and `render_videos(cache_root=…)` take them already resolved, the same rule `config.output.*` follows. (4) **The video fingerprint hashes screenshot *bytes*, not URLs** (`video.screenshot_urls` + the memo threaded through `job_fingerprint`), and excludes `_NON_VISUAL_OPTIONS` (`tts`, `cache`, `cache_dir`, `ffmpeg_path`, `timeout`) — a **denylist**, so a field added later is invalidating by default. Without the first half a recapture ships the old UI; without the second, setting an API key re-encodes the corpus.
- **Per-guide build layouts**: `steppy build` narrows its layout dimension per guide via `BuildAssembler._layouts_for_guide` = `BuildConfig.layouts` ∩ the scenario's frontmatter `layouts:` (build order preserved). This is the build-side half of the scenario-level declaration: without it a desktop-only flow ships a "Mobile" toggle swapping between identical screenshots. A scenario that declares nothing keeps the full dimension (byte-identical); a **disjoint** declaration is a `BuildError` (silently publishing the wrong screenshots is worse); a declared-but-uncaptured layout keeps the old warn-and-fall-back path (`_warn_layout_capture_missing`) so a failed capture can't silently shrink the site. `guide_layouts`/`guide_default_layout` are threaded into `_emit_static_guide`, `_emit_angular_guide`, `_emit_interactive_guide` and `_copy_screenshots`; the site `manifest.json` keeps the global `layouts` and adds the effective set per guide entry.
- **Per-layout screenshots (`screenshot.layouts`)**: `config.yaml` may declare `screenshot.layouts: { desktop: {width, height}, mobile: {...} }`. `steppy run --guide` auto-parametrizes over all configured layouts (cartesian with locales) and sets `STEPPY_LAYOUTS`. `steppy run --layouts desktop,mobile` (without `--guide`) does the same in test mode — useful to verify scenarios across device viewports without capturing screenshots. Conftest reads `STEPPY_LAYOUTS` into `LAYOUTS_FOR_RUN`, role page fixtures parametrize over `(locale, layout)` pairs, the active layout's viewport is applied to the browser context, and screenshots (when enabled) land under `output/screenshots/<scenario>/[<locale>/]<layout>/step-NN.png`. With no layouts parametrized, behavior is identical to today (single viewport, flat path).
- **Per-layout capture density (`device_scale_factor`) + no-upscale display cap**: fixes blurry mobile screenshots. A narrow mobile layout (e.g. 390px) captured at the Playwright default `device_scale_factor=1` yields a 390px-wide PNG that the guide then upscales to fill the ~900px content column → soft on high-DPI; desktop (1280px) escapes because it downscales. **Capture-side**: `LayoutConfig.device_scale_factor` (per-layout) and `ScreenshotConfig.device_scale_factor` (default/fallback), both `int` `Field(default=1, ge=1)` in models.py — default 1 keeps existing output byte-identical. `conftest.py.j2` (BOTH trees) bakes `LAYOUT_SCALE_FACTORS` (Jinja, mirrors `LAYOUT_VIEWPORTS`), adds `_get_scale_factor()` (reads `CONFIG["screenshot"]["device_scale_factor"]` at runtime) + `_get_scale_factor_for_layout(layout)` (mirrors `_get_viewport_for_layout`), passes `device_scale_factor=_get_scale_factor_for_layout(CURRENT_LAYOUT)` on every layout-viewport `new_context(...)`, and records it in the screenshot sidecar (readers default 1 when absent — the `_SIDECAR` test helper omits it). It sets **only** density — NOT `is_mobile`/`has_touch` — so the captured page layout is unchanged. Tradeoff: density scales pixels², so `device_scale_factor: 3` ≈ 9× the PNG bytes (≈4× at 2); bump it only on the narrow layouts that need it (usually `mobile`). **Display-side**: `.steppy-stage img` switched from `width:100%` to `width:auto; max-width:100%` in `guide.fragment.html.j2`, `guide.html.j2`, `static/guides.css` (both trees) and the player's `packages/player/src/templates/base-styles.ts`. An `<img>` with `width:auto; max-width:100%` renders at `min(intrinsic_px, container)` — reads the PNG's true pixels (so it respects the DSF automatically), fills the column when dense, and never upscales a low-res capture (it left-aligns at native size instead). This is simpler/more robust than threading an intrinsic-width var through the build. Player-specific care point: `captureSize` stays the CSS viewport (built from the sidecar `viewport` in `guide.py:prepare_interactive_manifest`), NOT PNG px, so the animator's cursor/hotspot math (`getDisplayScale = renderedRect / captureSize`, scaled bboxes are CSS-px) is unaffected by DSF; the img stays left-aligned (no centering) so the overlay origin (stage top-left) keeps matching the image top-left. Rebuild + re-vendor the player bundle after the base-styles edit (only `steppy-player.js` changes; the IIFE cursor bundle doesn't embed base-styles).
- **Build-time layouts (`BuildConfig.layouts`)**: `steppy.guide.config.ts` may declare `layouts: ['desktop', 'mobile']` and `defaultLayout`. `steppy build` then renders each guide once per (locale, layout) pair. The static target embeds all layouts in a single `<slug>/<locale>.html` page with `data-layout` wrappers and a small JS-driven toggle (mirroring how the locale switcher works, but client-side instead of separate URLs — this asymmetry is intentional). The Angular target emits `CONTENT[locale][layoutKey]` and the per-guide component owns a local `selectedLayout` signal (initial value = `defaultLayout`); the component uses `selectedLayout()` to pick the right fragment. Both targets show a layout toggle only when `len(layouts) > 1`.

When no per-layout subdirs exist, behaviour matches the pre-layout era (single guide per locale, flat output path). This auto-discovery is what lets `steppy guide` (and `steppy guide --guide`) consume screenshots captured under `<slug>/<locale>/<layout>/` without any new CLI flag — the layout dimension flows from disk shape, not from explicit config.

- **Parallel execution (`steppy run --workers N >= 2`)**: opt-in only. The single-worker path in `cli.run` (line ~497) is unchanged — its only addition is a lazy-import dispatch (`if workers >= 2: from steppy.coordinator import run_parallel; ...`) at the top of the try block. Guard tests in `tests/test_no_parallel_import_on_default_path.py` and `tests/test_run_byte_identical.py` enforce that `steppy run` (no flags or `--workers 1`) imports nothing from coordinator/worker/_parallel and produces a byte-identical pytest cmd + STEPPY_ env. Schema additions: `apps.<role>.internal_url` (per-app in-network URL workers use) and a top-level `parallel:` block (`workers`, `compose_file`, `worker_image`, `healthcheck_timeout`, `build_image`). Workers reach the app by splicing `STEPPY_BASE_URL_OVERRIDE` (JSON `{role: internal_url}`) into `CONFIG["apps"][role]["url"]` at conftest load time — no fixture-level branching. Compose override uses `!reset []` (Docker Compose 2.20+ required) to clear inherited host port mappings so multiple stacks coexist. Worker image auto-builds on first parallel run (skip with `--no-build`); tag = `<package_version>-<src_hash>` (hash **always** applied, over every `*.py` under the resolved package root, so a wheel reinstall of the same version can't silently reuse a stale image). Build inputs are resolved by `_parallel/image.py:resolve_build_inputs` in three modes: **config** (`parallel.dockerfile` + optional `parallel.build_context` — escape hatch for a custom worker image) → **repo** (a source checkout: `<root>/src/steppy` with a sibling `Dockerfile` **and** `pyproject.toml`; builds the repo-root `Dockerfile` against the repo root, unchanged from day one) → **installed** (everything else — steppy installed as a wheel with no source tree; `synthesize_installed_context` copies the installed package + its `.dist-info` (named after the distribution: `steppy_dev-<v>.dist-info`) + a `requirements.txt` derived from `importlib.metadata.requires(DISTRIBUTION)` into the run tmp dir and builds the wheel-bundled `src/steppy/_docker/Dockerfile.installed`, which puts the package on `PYTHONPATH` and adds a `steppy` console-script shim). The installed mode is what makes `steppy run --workers N` work off a plain `pip install` — the repo `Dockerfile` COPYs `pyproject.toml`/`hatch_build.py`/`src`/`templates`/`skills`, none of which exist in a wheel. It is sound because the worker only runs `python -m steppy worker` → pytest on the already-generated tests bind-mounted from the project; it never generates code. `parallel.worker_base_image` overrides the Playwright base on all three modes via `--build-arg PLAYWRIGHT_BASE=` (both Dockerfiles declare the ARG; the default is pinned in three places — `DEFAULT_PLAYWRIGHT_BASE`, both Dockerfiles — with `tests/test_parallel_worker_image.py` as the drift guard) and is folded into the image tag. `ensure_worker_image` probes the local image **before** resolving inputs (a warm image synthesizes nothing) — that probe is the seam where a future registry `docker pull` slots in. The work-stealing queue uses **O_EXCL claim files**, NOT `os.rename` — `os.rename` double-claims on Windows NTFS under heavy concurrency (~20% rate observed). Lifecycle: `ExitStack` + SIGINT handler guarantee `docker compose down -v` runs for every spawned stack on success, failure, or Ctrl-C. Orphan detection via `Queue.orphaned_running_tasks()`; orphans are now folded into the retry set (see below) rather than being fatal. `WORKER_IMAGE_CONTRACT` (image.py) is folded into the tag digest so an image-content change that touches no `*.py` (a Dockerfile edit, a new baked extra) still busts warm images — bump it whenever either Dockerfile changes. Both Dockerfiles install the `[retry,report]` extras (`runtime_requirements()` mirrors that for the synthesized context) because `--reruns` executes *inside* the container. See `coordinator.py`, `worker.py`, `_parallel/{queue,compose,image,lifecycle,progress,retry,fingerprint}.py`, `Dockerfile`, `templates/conftest.py.j2` (the splice block right after the credentials merge).
- **Report flags in parallel mode**: `--trace`/`--video`/`--retries` and the `--` pytest passthrough are resolved host-side by `cli._resolve_report_modes` (they need `config.yaml`) and travel to the workers as env vars — the coordinator has no pytest process of its own. `render_override` emits `STEPPY_TRACE`/`STEPPY_VIDEO`/`STEPPY_RETRIES`/`STEPPY_PYTEST_EXTRA` **only when non-empty**, so an unused feature leaves the rendered YAML byte-identical (guards: `tests/test_parallel_report_flags.py`, `tests/test_parallel_preauth.py`). The first two are read by the generated conftest; the last two by `worker._build_pytest_argv`. Any new worker-bound setting must follow the same conditional-emission rule.
- **Retry pass (`parallel.retry`, `--retry-pass N`)**: after the queue drains, failed scenarios (**plus orphans**) are re-run at reduced concurrency — default 1 worker, which is the point: a scenario that fails under N workers and passes alone is a *contention* flake, and retrying into the same contention (what `report.retries`/`--reruns` does) proves nothing. Cheap because the worker resolves everything from `STEPPY_COORD_DIR`: pointing attempt *n* at `<tmp>/retry-<n>/` gives it a private queue/claims/results tree, so **neither `worker.py` nor `queue.py` changed** and attempt 1's evidence survives beside attempt 2's. Only `steppy-worker` is recreated (`compose up -d --no-deps --force-recreate`), so app services, DB state and a completed `steppy-preauth` all persist. Two non-optional details: each pass needs a **fresh `EventBus`** (`_tests` is keyed `(worker_id, nodeid)` and `test-start` overwrites in place while `_counts` only increments — reuse corrupts both) and **fresh log tailers** (`compose logs -f` dies with the container it followed). `classify()` folds attempts into passed/flaky/failed; **FLAKY is lenient** (exit 0) unless `--strict-flaky`. Flaky slugs are excluded from the `lastfailed` cache so `steppy rerun` only re-runs real failures, and `failures.persist_failure_artifacts(log_roots=...)` maps each slug to its *final* attempt's coord root so the persisted `pytest.log` isn't a stale one. See `_parallel/retry.py`, `coordinator._finalize_run`/`_run_retry_passes`.
- **Failure grouping (`_parallel/fingerprint.py`)**: `normalize_tail` scrubs run-specific noise (timestamps, uuids, hex addresses, durations, absolute paths, line numbers, ports, bare ints) and `fingerprint` hashes the result, so one cause across forty scenarios prints as one *Failure causes* line instead of forty tracebacks. Normalization is deliberately aggressive — a false merge costs one extra glance, a false split puts the reader back to scrolling — but must still separate two different selectors (guard: `tests/test_failure_fingerprint.py`). The renderer shows the full tail only for each group's first scenario; `--verbose` prints them all.
- **Results bundles (`steppy run --bundle` → `steppy bundle create`)**: the producer half of the versioned contract a control plane consumes. Six decisions carry it. (a) **Recorder dumb, interpreter smart** — same split as the coverage recorder/merge: the pytest plugin writes raw per-test JSONL, and *all* attribution (which scenario, which locale, which run) happens in `bundle/`. (b) **Three env gates, each inert when unset** — `STEPPY_EVENTS_DIR` (JSONL sink), `STEPPY_JUNIT_DIR` (fixed-path `--junitxml`), `STEPPY_RUN_ID`. `--bundle` sets all three; nothing else does, which is what keeps `tests/test_run_byte_identical.py` green. Parallel mode plumbs the first two through `render_override`'s conditional `extra_env` block. (c) **Per-run directories, never a reset step** — `output/events/<run-id>/` mirrors `output/coverage/raw/<run-id>/`, so yesterday's records can never be mistaken for today's; and per-**scenario** junit files, because N workers share one `output/` mount and one fixed path would leave only the last finisher's report. (d) **`(scenario, locale, layout)` comes from `item.callspec.params` and `module.SCENARIO`, never from parsing a nodeid** — `fr-BE` contains the id's own separator. Captured in `pytest_runtest_protocol`, which fires before `logstart`; `runtest_setup` is too late and files every `test-start` under `unknown`. (e) **The nodeid sanitiser is lossy, so build the forward map** — sanitise the nodeids the run reported and look filenames up in it; never invert one. `captures.sanitise_nodeid` is byte-mirrored with `conftest.py.j2` (guard: `tests/test_captures.py`), the same arrangement as `_totp_now`. (f) **Step granularity is a `bracket_step` generator filter, not template lines** — every step body is wrapped in `_steppy_mark_step` / `_steppy_end_step` (conftest helpers, gated on `STEPPY_STEP_EVENTS=1`, which `--bundle` sets and `STEPPY_STEP_EVENTS=0` opts out of), and `manifest.tests[].failed_step` is the step that started and never ended. It is a Python filter because whether a captured body ends with a newline **depends on which action branch rendered** — one whose last literal is followed by `{%- elif %}` has it stripped at lex time — so a template-level marker glued onto the previous statement for `wait` alone. Applied *before* `apply_step_guard` so a step skipped by `only-in:`/`layouts:` emits neither marker and can never be blamed. (g) **Archives are byte-reproducible** — sorted members, `mtime=0`, normalised ownership/mode, PAX, no directory entries, `run.created_at` taken from the run's sidecar rather than the clock, and `gzip.GzipFile(filename="", mtime=0)` because both the timestamp *and* the embedded output filename would otherwise vary. Without that, the content-addressed upload protocol re-sends everything every time. **`truncated` means the size budget dropped something that belonged in the bundle** — never a flag-excluded artifact, or a consumer cannot tell "step 7 never ran" from "we dropped step 7".
- **Bundle upload (`steppy bundle upload`)**: the client half of the protocol above, and the first thing in this repo that talks to a control plane. Six decisions. (a) **A locally-executed run is one whole-run task the uploader claims** — `POST /v1/runs` (`executor: local`) → `/claim` → offer/PUT/finalize → `POST /v1/tasks/{id}/complete`. Not a special "push" endpoint: the plane's `close_if_finished` refuses to judge a run with no tasks (so a taskless run never ends) and its watchdog orphans a seeded task nobody claims (so the run lands on `failed`). Claiming makes cancellation, leases, task counts and the verdict SQL all apply unchanged — and it is exactly `steppy ci run` minus the running. (b) **Finalize before complete.** Reversed, `close_if_finished` runs with no bundle pending, lands a terminal verdict, and the close statement then refuses to move a terminal run to `ingesting`; the results still arrive but the status already said they were not coming. For a claim-token uploader the plane enforces it — `complete` nulls `claim_token_hash`, so completing first throws away the credential the upload needs. (c) **No archive is written.** The protocol is per-file, so a `.tar.zst` would be created only to be read back; live-tree mode goes through `plan_bundle` + `archive_members` and never re-derives a path (`junit.xml` and `events/*.jsonl` are generated and have no file under `output/`). (d) **Two httpx clients.** A presigned URL carries its authorisation in the query string, and a store receiving a presigned signature *and* an `Authorization` header rejects the pair as a 400 that reads like a bad URL — so blob PUTs go out on a client with no default headers. Same trap as the plane's `?redirect=false`. (e) **Resumability is free, not bookkept.** The offer is keyed `(run, task)` and reports `already_held`, so re-offering after a partial upload returns only the remainder; an expired presigned URL (403/400) triggers exactly one re-offer, and a second expiry means the server's URL TTL is shorter than one blob takes. Progress is counted as it happens (`_Sent`), never inferred from the next offer. (f) **The bundle's `run.run_id` is the `Idempotency-Key`**, so a retried upload attaches instead of burning a second run number — which only holds when the run *has* a recorded identity, i.e. after `steppy run --bundle`. Counting note: `uploaded`/`already_held` are in **blobs**, `total_files` in manifest entries; a real capture ran 3204 files → 1587 blobs, so reporting one against the other reads as a discrepancy.
- **Run history (`.steppy/history.jsonl`)**: `steppy.history` is a **leaf module** (stdlib only, imports nothing from `cli`/`coordinator`/`_parallel`) writing one append-only JSON record per (run, scenario) from `coordinator._finalize_run`. Lives in `.steppy/` and **not** `output/` for the same reason the coverage store does — `output/` cleanup would wipe it, and history that evaporates on a clean build is worse than none because it still looks authoritative. Readers skip malformed or future-`v` lines rather than raising (a killed process leaves a torn line). Consumed by `steppy flaky` (`flaky_cli.py`, registered via `register_flaky(app)` like `coverage_cli`) and by the coordinator's longest-first queue ordering.
- **Queue ordering**: `Queue.seed` writes `NNNN-<task_id>.task` so `claim()`'s sorted walk honours **seed order**, not the alphabet; `claim`/`is_empty` strip the prefix and claim/result files stay keyed by the bare id (so orphan detection is untouched). Un-prefixed task files still drain, for a queue dir seeded by an older steppy. The coordinator seeds longest-first from `history.median_durations` via `_order_tasks_longest_first` — weight is the **sum** over a task's members, because an exclusion group is one scheduling unit (unknown-weight tasks last — most likely newly added, and guessing they're slow would push a genuinely slow known one behind them); no history ⇒ unchanged order. A `task_id` is a scenario slug unless the entry is an exclusion group, in which case it is the group name.
- **Exclusion groups (`exclusive:` frontmatter)**: two scenarios naming the same group never run concurrently under `--workers N`; different groups still do. The mechanism is a **partition, not a protocol** — `exclusive.partition` (a stdlib-only leaf at `src/steppy/exclusive.py`, imported by `models.py` on the eager path *and* by `_parallel/queue.py`) collapses each group into ONE queue task on the host before any container exists, and `worker_main` runs its `task.slugs` sequentially with one pytest process each. So there is no lock to leak on `kill -9`, no lease, no timeout, no waiting state, and no worker ever waits on another; the only run-time primitive is the O_EXCL claim that already existed. **Results, logs, JUnit and the `scenario-start/end` events stay keyed per SCENARIO** even for a batch, which is what lets `failures.py`, `lastfailed.py`, `history.py`, `classify()` and the renderer stay untouched. Six things are load-bearing: (a) `seed(slugs, *, batches=None)` keeps `slugs` a `list[str]` of task ids and the keyword is **omitted** when nothing is grouped — three existing test spies are declared `(self, slugs)`, and an unconditional `batches=None` breaks them; (b) the batch map is **Queue state** set by `seed`, never a parameter, because `orphaned_running_tasks()` has three call sites (`coordinator.py:98`, `coordinator.py:815`, `retry.py:276`) and the one that is easiest to miss decides *what gets retried* — unmapped, it reports the group NAME as a failed scenario and retries a test file that does not exist; (c) group names are **lowercase-only** and task ids are checked for `casefold()` collisions, because the coord dir is `mkdtemp`'d on the host and NTFS/APFS would merge `Payments` with `payments` into one claim file and silently drop a whole task; (d) `partition` keys grouped and ungrouped entries **separately**, so a group named after an ungrouped slug yields two colliding ids (an error) instead of one task that swallows the loose scenario and never runs it; (e) `effective_workers` is capped at the task count, and the pre-existing `< 2` bail must **not** `return 0` when a collapse is the cause — every scenario in one group is the most obvious first use, and that branch would report success having executed nothing; (f) `Queue.unclaimed_slugs()` + `PassResult.never_started` are the backstop for a task nothing ever claimed (invisible to both `orphaned_running_tasks` and `collect_results`) — it joins `pending_slugs` for the retry but **not** `failed_slugs`, or a scenario that never ran and then passed would be reported FLAKY and poison `.steppy/history.jsonl`. A retry pass **regroups inside the attempt loop** (`pending` is reassigned per attempt). Deliberately not done: one pytest invocation over K files — it would amortise a browser launch but breaks per-scenario exit codes, per-slug JUnit, per-slug logs, crash attribution and the `_steppy_events` module-state assumption; `Task.slugs` is a list either way, so the door stays open.
- **Circuit breaker (`parallel.circuit_breaker`, `--fail-fast/--no-fail-fast`)**: `_wait_for_workers` gained an `on_poll` hook fired each 1.5s cycle **while workers are still pending**; the coordinator's callback raises `_CircuitBreakerTripped` once `min_completed` scenarios reported AND `fail_ratio` of them failed. Both thresholds are load-bearing — the ratio alone trips on the first failure of a run, the count alone trips on a merely-red suite, and a breaker with a false-positive reputation gets switched off. A trip skips the retry pass (infra, not flake) but still runs the normal finalize + teardown.
- **`parallel.isolate_auth`**: the shared `.auth` is bind-mounted **read-write into every worker**, so N workers race on one storage-state file. Enabling this gives each worker a private, pre-seeded `tmp_dir/auth/w<i>` mounted at `/steppy/project/.auth` (trading one login for N). **Mutually exclusive with `pre_auth`** — enforced by a `model_validator` on `ParallelConfig`, not a silent preference, because the failure mode otherwise is "workers are unauthenticated and nothing says why".
- **Parallel pre-authentication (`parallel.pre_auth`)**: optional hook that fixes storage-state auth in worker mode. Playwright storage state is **origin-bound**, so a session captured on the host (`http://localhost:4200`) does NOT authenticate workers, which reach the app at the in-network `internal_url` (`http://app-frontend:80`) — every scenario bounces to login. `parallel.pre_auth` (`PreAuthConfig`: `command`, `timeout`, optional `image`; models.py) makes the coordinator render a one-off `steppy-preauth` service into each worker's compose override (`render_override`, compose.py) that runs `command` **in-network** (reusing the worker image + the project-RO/`.auth`-RW mounts + `STEPPY_BASE_URL_OVERRIDE`), gated so `steppy-worker` waits for it via Compose `depends_on: service_completed_successfully`; `steppy-preauth` itself `depends_on` every user service that declares a healthcheck (`introspection.services_with_healthcheck`), so the login only runs once the app is serving. The N per-worker stacks each render a preauth service, so it is deduped once-per-run across stacks by a Steppy lock-wrapper (hidden `steppy _preauth-run`, `_parallel/preauth.py`) using the same **O_EXCL** claim primitive as the queue: one winner runs `command` + drops a `preauth.done` sentinel, losers wait for it. Unset ⇒ inert (the rendered override + dispatch are byte-identical; guarded by `tests/test_parallel_preauth.py`). Runtime-only — **no conftest/template/schema/player change**; storage-state files are consumed verbatim (`conftest.py.j2:431`). The command itself is a project concern; the reference implementation (a project's own `auth_login.py --internal`) logs in at the internal origin and **merges** it into the existing `.auth/<role>.json` (origins + cookies unioned) so one file serves both single- and multi-worker mode — and applies the same insecure-origin PKCE polyfill the conftest uses, since `http://app-frontend` is not a secure context. Touch points: `PreAuthConfig` + `ParallelConfig.pre_auth` (models.py); `ComposeIntrospection.services_with_healthcheck` + the preauth block in `render_override` (compose.py); the `pre_auth_*` args threaded from `coordinator.run_parallel`; `_parallel/preauth.py` + the hidden `_preauth-run` command (cli.py). See also the drift guard `tests/test_config_schema.py` (regenerate `steppy-config.schema.json` after model edits).
- **Parallel + guide mode**: `--workers N --guide` composes cleanly. Each scenario is claimed by one worker; that worker's pytest invocation handles ALL (locale × layout) parametrizations sequentially in one process (browser launched once, auth amortized). Screenshots and JSON sidecars land in the shared `output/` bind mount at the same paths a single-worker `--guide` run produces (`output/screenshots/<scenario>/[<locale>/][<layout>/]step-NN.png` + sidecars; multi-frame fill-form emits `step-NN-{a,b,c}.png`). `steppy guide --guide` and `steppy build` are pure disk readers — they don't care if the run was parallel. The env-var contract (`STEPPY_LOCALES`, `STEPPY_LAYOUTS`, `STEPPY_GUIDE_MODE`, `STEPPY_NO_ASSERTS`, `STEPPY_SCREENSHOTS` all flowing CLI → `coordinator.run_parallel` → compose override → worker container → conftest) is pinned by `tests/test_parallel_guide_integration.py` (no Docker). Manual end-to-end recipe in `tests/integration/README.md` section 6. **Caveats**: (a) `.auth/<role>.json` is bind-mounted RW across workers; if each stack has an isolated DB, set `auth.storage_state_ttl: 0` in `config.yaml` to force per-worker re-auth. (b) `seed/<name>.py` scripts run **inside** the worker container — host URLs (`http://localhost:5432`) won't resolve. Seeds should read `STEPPY_BASE_URL_OVERRIDE` (JSON `{role: internal_url}`) and fall back to the host URL when unset (single-worker mode).
- **Security posture (see `SECURITY.md`)**: four hardening measures, all with safe defaults so existing output/config is unaffected. (1) **`${VAR}` / `${VAR:-default}` config interpolation** — `config._interpolate_env` resolves env refs in every string leaf of `config.yaml`/`credentials.yaml` at load time (used by `auth.py`), mirrored by `_interp_env` in **both** `conftest.py.j2` trees so refs also resolve at test runtime (worker/CI env). `config._check_credential_hygiene` warns (stderr) on plaintext `apps.*.auth.credentials` literals in the committed config. Shipped `config.yaml` now uses `${STEPPY_<ROLE>_USERNAME/PASSWORD}`; `credentials.yaml.example` documents the gitignored overlay. (2) **JS injection fix** — `auth.py` localStorage injection passes `page.evaluate("([k,v]) => localStorage.setItem(k,v)", [k, v])` instead of f-string interpolation (conftest's locale inject was already safe via `json.dumps`). (3) **`security.allow_shell_capture`** (`SecurityConfig`, models.py; default **false**) gates `capture from.type=shell` in both conftest trees; when enabled, `_interp_shell` `shlex.quote`s each interpolated `{{var}}` (which may be DOM/HTTP-sourced) so page content can't inject. (4) **Screenshot redaction** — `ScreenshotConfig.mask` (CSS selectors) + `mask_color` drive `_screenshot_mask_kwargs(page)` (both conftest trees), passed as Playwright `mask=`/`mask_color=` on every `page.screenshot`; empty mask ⇒ `{}` kwargs ⇒ byte-identical output. `.auth/<role>.json` gets `os.chmod(0o600)` after each `context.storage_state` write (`auth._restrict_permissions`, POSIX-only, best-effort).
- **Coverage map (`steppy run --coverage` + `steppy coverage ...`)**: deterministic substrate for gap analysis — record → merge → store → report, zero LLM involvement, framework-agnostic (URL/History API/V8 coverage/network only). **Recorder** lives in `conftest.py.j2` (BOTH trees): env-gated on `STEPPY_COVERAGE=1`, `_coverage_start` after `_attach_page_diagnostics`, `_coverage_stop_and_write` before `page.close()` in both fixture variants; route trail = `framenavigated` (authoritative — Playwright counts History-API changes as navigations) + injected history hook for push/replace/pop/hash tagging; JS coverage via CDP `Profiler.startPreciseCoverage` (playwright-python has NO `page.coverage` API); raw records (lossless, schema `steppy_coverage_record: 1`) land at `output/coverage/raw/<run_id>/<scenario>/<fixture>__<locale-layout>.json`, inline `data:` source maps gzipped under `_maps/<sha256>.json.gz`. **Merge** (`steppy/coverage/merge.py`) does ALL interpretation (route `:id` normalization, API attribution by `base_urls` longest-prefix, observed→declared template matching, source-map VLQ decode with disk lookup in `coverage.sourcemap_dir` → bundle-granularity fallback) and upserts transactionally: `DELETE WHERE scenario_id` + insert, so re-running a scenario replaces its contribution (idempotency pinned by `tests/test_coverage_store.py` / `test_coverage_gaps.py`). **Store** sqlite at `.steppy/coverage.db`: nodes identity `(kind, api, method, key)` with `'' NOT NULL` (SQLite UNIQUE treats NULLs distinct), provenance DERIVED at read time (declared = manifest row, tested = declared ∩ covered, discovered = covered only); `triage` table (`ui_testable|non_ui|unknown`) is never touched by merge/refresh; nodes never deleted. **Refresh** re-links observed endpoint nodes onto newly declared templates via evidence samples — merge↔refresh order-independent. Touch points when extending: record schema version in BOTH `conftest.py.j2` trees + `merge.RECORD_SCHEMA_VERSION` (sync pinned by `tests/test_coverage_record_template.py`); `CoverageConfig`/`CoverageApiConfig` (models.py); `--coverage` flag + `coverage_app` group (cli.py, all imports lazy — guard `tests/test_no_coverage_import_on_default_path.py`); `STEPPY_COVERAGE` compose env line (`_parallel/compose.py`) + coordinator post-`collect_results` merge.

## The control plane, and the boundary with it

Steppy has a commercial control plane, developed **outside this repository** and
not required by anything here. What matters inside this repo is the boundary, and
this is the side that has to stay clean.

- **The boundary rule is physical.** *Transforms artifacts → here; remembers,
  compares, coordinates, or serves people → the control plane.* No `ee/` folder,
  no licence check, no billing code, no plan gate ever lands in this repository.
  The clients that talk to a plane (`steppy bundle upload`, and later
  `steppy ci run` / `steppy agent`) are the exception that proves it: they run
  inside a customer's CI touching their repo and credentials, so they are OSS on
  purpose. A closed binary doing that fails the exact security review Steppy's
  positioning is built on passing.
- **The dependency direction is one-way.** A plane pins a steppy version and
  speaks the versioned bundle/report contracts. Nothing here imports anything
  from there, and **no feature here may assume a control plane exists** — the
  free path has to stay excellent on its own.
- **When adding a user-facing feature here, check whether it changes a contract
  a plane consumes**: the screenshot sidecar keys, the `output/` tree shape, the
  `STEPPY-EVT::` grammar, or `cli._build_run_env`'s env vars. All four follow the
  same forward-compat rule the sidecars already do — add fields, never repurpose
  them, and let readers default what is absent.
